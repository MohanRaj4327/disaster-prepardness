CHAPTER 1 – INTRODUCTION
1.1 Purpose
The purpose of this software Requirement Specifications (SRS) document is to describe the technical architecture and specifications for the real-time project Disaster Preparedness and Response Education System for students and educational campuses. The system helps students gain critical knowledge about disasters and preparedness, execute mock drill simulations, and utilize a grievance system to report and resolve man-made campus safety hazards. The project is implemented as an enterprise Java web-based platform.

1.2 Scope
The platform provides features where user can:
Learn about disaster preparedness
Learn by simulations
Submit grievances for man-made disasters (blocked exits, exposed wires, gas leaks)
Track grievances in real time
The admin can:
View grievances
Analyze safety reports
Add, edit, remove drills and learning modules
Broadcast emergency alerts across campus
Monitor actions and audit compliance

CHAPTER 2 – OVERALL DESCRIPTION
2.1 Product Perspective
The web application connects students, teachers, administrators, and campus emergency responders. The system provides secure role-based access for Students, Teachers, and Administrators. Grievances and audit reports are stored and managed through Java enterprise data persistence with thread-safe concurrency.

2.2 Product Functions
User management:
student registration
teacher registration
Administrator registration
Authentication & Token Authorization

Disaster Learning:
Video lessons & interactive tutorials
Safety guidelines & DOs / DONTs checklists
Offline emergency PDF resources
Comprehensive disaster encyclopedia

AI assistant:
Disaster awareness AI chatbot
Immediate emergency guidance & triage
Searchable FAQ engine

Mock drill Management:
Schedule mock drills
Real-time attendance tracking
Performance evacuation time & safety score evaluation

Evaluation manager:
Interactive building and campus maps
Safe fire exits and primary assembly points
Trauma AED and fire extinguisher station markers

Quiz modules:
MCQ safety quizzes
Automated score analysis
Official verifiable safety certifications

Reporting:
Preparedness reports
Risk reports
Student progress and evacuation audit logs

2.3 User Characteristics
Student can: learn, attend quizzes, view alerts, receive certificate, report hazards.
Teacher can: Create learning modules, schedule drills, conduct assessments, monitor students.
Admin can: Manage users, broadcast campus alerts, assign departments, audit safety logs.

2.4 Operating Environment & Technical Constraints
High-performance Java 26 Virtual Threads (Project Loom).
Prevent unauthorized exposure to personal information via role-based access.
Duplicate complaints prevented with atomic IDs.
TLS 1.3 / HTTPS encryption.

2.5 Assumptions and Dependencies
Assumptions:
Users have access to web browsers on desktops, laptops, tablets, or smartphones.
Educational institution maintains student enrollment records.
Dependencies:
SMS and email gateway APIs.
Mapping and floorplan visualization services.
Java Standard Edition runtime environment.

3.4 Logical Database Requirements & Java Entity Model
1. USER (org.disaster.model.User): id, name, email, password, phone, role, institution, createdAt
2. Complaints (org.disaster.model.Complaint): id, userId, userName, category, title, description, location, image, status, priority, departmentId, assignedOfficer, resolutionNotes, createdAt, updatedAt
3. Learning module (org.disaster.model.LearningModule): id, name, category, type, summary, fullDescription, dos, donts, keyActions, videoUrl, emergencyEquipment
4. Feedback (org.disaster.model.Feedback): id, complaintId, userId, userName, rating, comments, createdAt
5. Drill (org.disaster.model.Drill): id, title, disasterType, building, assemblyPoint, scheduledDate, status, expectedParticipants, attendedUserIds, evacuationTimeSeconds, safetyScore, evaluatorTeacher, evaluationNotes, createdAt
6. EmergencyAlert (org.disaster.model.EmergencyAlert): id, title, message, severity, disasterType, targetAudience, issuedBy, active, createdAt
7. Department (org.disaster.model.Department): id, name, assignedOfficer, phone, email

3.5 Java Design Constraints
Use Enterprise Java SE 26 Architecture
Embedded HttpServer with Virtual Thread executors
Follow clean REST API architecture
Responsive Single Page Web Application UI with Vanilla CSS
Pure Java DOCX Extraction utility (org.disaster.util.ExtractSRS)

3.6 Software System Quality Attributes
Security: Role-based access, token session authorization, input validation
Reliability: Thread-safe data persistence and automatic disk snapshots
Scalability: Virtual Threads capable of high concurrency loads
Usability: Clean glassmorphic dashboard with dark/light themes
Maintainability: Clear MVC/Service layer architecture
Portability: Operates on any OS hosting standard Java runtime

3.7 Architectural Workflows & Object Oriented Model Classes
1. User: register, login, report complaint, take quiz, view certificates
2. Admin: login, broadcast alerts, verify complaints, assign departments, update status, audit reports
3. Complaint: id, category, description, image, priority, status
4. Department: department Id, department name, assigned officer, phone, email
5. EmergencyAlert: alert ID, title, message, severity, timestamp, active
6. Feedback: rating, comments, complaint ID
7. Drill: schedule, attendance, evacuation time, safety score
8. Quiz: question generation, answer evaluation, certificate issuance
